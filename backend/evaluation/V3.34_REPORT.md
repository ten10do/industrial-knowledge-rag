# V3.34 Identity-aware Evidence Reasoning

**IDENTITY_GENERALIZATION_READY**

The pre-implementation audit found that current identity compatibility is

and make a broad series statement appear exact. The detailed audit and the six

`V334_IDENTITY_FAILURE_ANALYSIS.md`.

## 2. Identity model design

V3.34 uses a lightweight deterministic identity profile:

```text
manufacturer
family
series
model
module
option
firmware
protocol
parameter
scope_level: GLOBAL | FAMILY | SERIES | MODEL | MODULE | OPTION
```

It separately extracts query identity and candidate-claim identity. Explicit
claim text takes precedence over document scope; document metadata supplies a
bounded vocabulary and is an exact-model fallback only for an unambiguous
single-model document.

Compatibility is directional:

- exact model query + same exact model claim: compatible;
- family or series query + matching descendant model claim: compatible;
- exact model query + family or series claim: incompatible;
- module query + controller-only claim: incompatible;
- option/accessory query + base-series or different-option claim: incompatible;
- explicit firmware X + firmware Y claim: incompatible;
- explicit parameter X + parameter Y claim: incompatible;
- insufficient reliable identity information: unknown, preserving existing
  behavior.

The core invariant is that a more specific query cannot be justified by
broader evidence.

## 3. Implementation

The implementation is additive in
`backend/retrieval/identity_reasoning.py`, versioned as
`identity-aware-evidence-v334-candidate` with status
`EXPERIMENTAL_CANDIDATE`.

The execution boundary is:

```text
query
  -> query identity extraction
  -> candidate-claim identity extraction
  -> directional compatibility
       COMPATIBLE   -> unchanged V3.32 mixed Evidence
       INCOMPATIBLE -> ABSTAIN / IDENTITY_SCOPE_MISMATCH
       UNKNOWN      -> unchanged V3.32 mixed Evidence
```

The wrapper records the query path, boundary status, per-candidate identity
diagnostics, delegation state, and final decision source. It has no upgrade
authority: it cannot convert an existing abstention to an answer.

`EvidenceDecisionV2` was not changed. No retrieval, BM25, dense retrieval, RRF,
reranker, parser, support gate, NLI threshold, or open-sufficiency threshold was
modified. The V3.25/V3.30/V3.32 modules and `support-v316.1` remain unchanged.

## 6. Failure analysis and experiment log

The candidate boundary classified 25 cases as `COMPATIBLE` and 25 as
`INCOMPATIBLE`; no benchmark case depended on an unknown identity fallback.

| Boundary reason | Count |
| --- | ---: |
| Exact model | 17 |
| Broader evidence scope | 10 |
| Exact module | 5 |
| Module-to-controller leakage | 5 |
| Firmware mismatch | 3 |
| Exact option | 3 |
| Option scope mismatch | 2 |
| Parameter scope mismatch | 5 |

Only one candidate experiment was performed:

| Experiment | Hypothesis | Change | Result | Decision |
| --- | --- | --- | --- | --- |
| V334-E1 | Directional claim identity rejects broader/sibling evidence without rejecting exact evidence | add claim-level identity boundary | FA -80 pp; FR +0 pp | accept for next sealed validation |

The pre-registered gate required a meaningful FA reduction of at least 10
percentage points and an FR increase no greater than five percentage points.
V334-E1 passed both conditions, so experimentation stopped at 1/3.

Known limitations:

- this is a controlled synthetic DEV benchmark, not an untouched manual
  generalization gate;
- extraction requires explicit identifiers or corpus metadata vocabulary and
  does not resolve unrestricted natural-language coreference;
- an `UNKNOWN` boundary intentionally preserves the old decision and therefore
  cannot fix identity omissions it cannot recognize;
- multi-candidate evidence is allowed when at least one explicit compatible
  claim exists; mixed compatible/incompatible claim aggregation requires
  sealed-manual observation before any further policy is justified.
