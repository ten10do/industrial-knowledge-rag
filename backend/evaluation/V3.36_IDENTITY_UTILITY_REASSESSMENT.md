## 2. Failure taxonomy and V3.34 before audit

The unmodified V3.34 implementation was recorded before candidate code was
changed. Its implementation SHA-256 was
`e6f2f425f25a148fa2a0053ba8269783e5fbba3597e88cd73456b494934b8685`.

V3.34 correctly rejected all 30 hard negatives, but refused all 30 answerable
safe-variation cases:

| V3.34 false-refusal cause | Count | Interpretation |
| --- | ---: | --- |
| `MODEL_MISMATCH` | 6 | base-model query versus explicit child variant |
| `FIRMWARE_MISMATCH` | 3 | exact query version covered by an “or later” evidence floor |
| `OPTION_MISMATCH` | 2 | base option versus documented option variant |
| `MODULE_MISMATCH` | 4 | base module versus child module variant |
| `BROADER_EVIDENCE_SCOPE` | 12 | explicit universal document/family claim rejected for a listed model |
| downstream rule after `EXACT_MODULE` | 3 | identity passed, but document-model metadata caused the existing Evidence rule to refuse |

The before boundary returned 57 INCOMPATIBLE and three COMPATIBLE decisions.
The dominant utility problem is therefore over-strict identity equivalence,
plus a representation gap between claim-level module identity and the existing
document-model Evidence view. It is not a retrieval or runtime failure.

The five semantic classes are treated as follows:

### A. TRUE_IDENTITY_CONFLICT

Sibling models, different modules/options, and incompatible firmware versions
remain mandatory abstentions. Same family or similar spelling is insufficient.

### B. COMPATIBLE_IDENTITY_VARIATION

A base identity may be supported by an explicitly named child variant, such as
`VX500` by `VX500-0123`. The direction is one-way: a base-model claim still
cannot establish a more specific variant query.

### C. SUBMODULE_IDENTITY

Exact modules and directional module variants are compatible. Controller-only
claims and sibling modules remain incompatible.

### D. DOCUMENT_SCOPE_IDENTITY

Being in the same manual is not enough. A broad claim covers a listed model
only when metadata declares `ALL_LISTED_MODELS`, the query model is in that
coverage list, and the claim contains an explicit universal marker such as
“all”, “every”, or “each”.

### E. PRODUCT_FAMILY_RELATION

The same explicit-universal rule applies to family claims. Local overview,
optional, unlisted, and unknown family relations stay blocked.

## 3. Candidate design

The only runtime implementation changed is
`backend/retrieval/identity_reasoning.py`, versioned as
`identity-v336-candidate`. Candidate SHA-256 is
`b8defb4a2987b27eb22536538f49b52c5f77e50d24b788b55ed025b4d0f5a753`.

The candidate adds four bounded utility mechanisms:

1. Directional descendant matching for model, module, and option suffix
   variants. `base -> base-variant` is compatible; the reverse remains a
   mismatch.
2. Numeric firmware-floor matching for explicit “or/and later/newer/higher”
   claims. Exact mismatches without a floor remain incompatible.
3. Explicit universal document/family coverage requiring both a lexical
   universal marker and a frozen covered-model list.
4. A local identity-aligned Evidence view for claims already classified
   COMPATIBLE. It clones candidate metadata for the call, aligns the proven
   query identity, delegates to the unchanged mixed Evidence contract, and
   never mutates retrieval results or stored documents.

The aligned view is unavailable to INCOMPATIBLE and UNKNOWN claims. It has no
authority to turn an identity conflict into an answer. Existing retrieval,
parser, Evidence contract, NLI, support, and open-sufficiency implementations
are unchanged.
