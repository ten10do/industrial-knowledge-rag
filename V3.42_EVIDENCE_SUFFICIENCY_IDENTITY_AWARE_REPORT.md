## 3. Benchmark design

`v342-evidence-sufficiency-identity-aware-dev-v1` contains exactly 60 unique English queries:
30 ANSWER and 30 ABSTAIN. Each of the six required cases has 10 queries with a 5/5 label split:

| Case | Queries | ANSWER | ABSTAIN |
|---|---:|---:|---:|
| Identity-compatible evidence recovery | 10 | 5 | 5 |
| Technical synonym | 10 | 5 | 5 |
| Abbreviation | 10 | 5 | 5 |
| Parameter table relation | 10 | 5 | 5 |
| Section inherited evidence | 10 | 5 | 5 |
| Cross-reference evidence | 10 | 5 | 5 |

The corpus uses two new, official manufacturer PDFs, with no repository match for either
product before acquisition and no use of A-H, J, K, or historical sealed data:

   SHA256: `5ccd502a8db4b7ab2d3c5ddcd8b0f29d70f8de415fd1bdb0177740a45c8e14b9`.
2. Balluff, *BNI IOL-302-002-E012 IO-Link 1.1 Sensor/Actuator Hub User's Guide*, English,

   `https://assets.balluff.com/WebBinary1/MAN_BNI_IOL_X0X_002_E012_EN_A21_DOK_931699_03_000.pdf`.
   SHA256: `7609566bc9e1f7033293b7b52199838a17bfbc631dadcded0eb61178372224bf`.

Both files passed metadata, page-count, English-text, rendered-page, and production-ingestion

Every ANSWER annotation binds a verbatim evidence key to one production chunk before freeze.
Every row explicitly records target, relation, attribute, value/action, expected relation,
identity compatibility, and parser recoverability. The 30 ABSTAIN rows cover all required hard

- same family, wrong parameter;
- same manufacturer, wrong model;

Gold-chunk positives and corpus-wide hard negatives passed a 60/60 static relation preflight
before the metric run. Baseline and candidate subsequently used production hybrid retrieval
with `k=5`; the candidate replayed the exact selected baseline candidates.

## 4. Implementation

The independent candidate is `evidence-v342-sufficiency-candidate`. It composes on top of
`identity-v341-claim-expansion-candidate`; it does not call an older identity path and does not
modify V3.41.

`EvidenceSufficiencyRelation` has exactly five outputs:

- `DIRECT_SUPPORTED`
- `SEMANTIC_SUPPORTED`
- `REFERENCE_SUPPORTED`
- `INSUFFICIENT`
- `UNSAFE`

Every relation includes `reason_code` and `confidence`, plus the bound chunk/document, target,
relation anchor, attribute anchor, and value/action anchor when present.

The decision gate is deliberately narrow:

1. Run V3.41 unchanged.
2. Preserve every V3.41 ANSWER.
3. Preserve every non-COMPATIBLE identity decision and every non-VERIFICATION path.
4. For a remaining refusal, require one retrieved chunk to bind target + relation + attribute
   + value/action.
5. Relax only a supported relation at confidence >= 0.82.

Technical synonym and abbreviation handling uses a closed industrial vocabulary, not corpus-
wide semantic expansion. Parameter-table rows are bounded by their DPP row, two-model column
values are assigned by column order, and explicit inline sibling-model mappings are checked.
Section evidence must carry the requested section anchor inside the same chunk. Cross-reference
support requires the concrete reference target after the queried attribute anchor.

## 8. Safety analysis

- Identity compatibility is only an entry precondition; it never produces an automatic ANSWER.
- Target, relation, attribute, and value/action must be present in one candidate chunk.
- No component is joined across candidates or documents.
- Unknown model tokens return `CROSS_MODEL_LEAKAGE_BLOCKED`.
- A value owned by a sibling table column or inline sibling model returns
  `SIBLING_MODEL_VALUE_BLOCKED`.
- Parameter values and indices are bounded to one DPP table row, preventing parameter borrowing.
- Section anchors are checked in the same chunk, preventing cross-configuration inheritance.
- Reference targets are associated after the queried attribute anchor, preventing page-number
  borrowing from an adjacent row.
- Manufacturer mismatch, wrong attribute/value, missing action/value, negated relaxation, and
  non-verification paths remain refusals.
- Candidate unsafe relax = 0. Candidate FA increase = 0 pp.
