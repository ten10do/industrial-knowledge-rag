## Root Cause

The benchmark harness built `RetrievalCandidate(document, retrieval_source="chroma")` and populated only `fusion_score = -distance`, never `vector_score`. The Evidence runtime reads `top.vector_score`, so `vector_distance` was `None` and the `max_vector_distance` gate was never evaluated. The production path `backend/rag_core._vector_candidates` already wires `vector_score = float(score)`, which proved the fix is confined to the harness/adapter boundary.

## Score Source Audit

The authoritative score is the distance returned by `langchain_chroma.Chroma.similarity_search_with_score`, documented as "distance in float for each. Lower score represents more similarity." It flows through `rag_core.retrieve_docs` as the second element of each `(Document, score)` tuple.

## Score Semantics

```
DISTANCE_METRIC     = Chroma raw distance (L2 on unnormalized sentence-transformers embeddings)
DISTANCE_LOWER_IS_BETTER = TRUE
CURRENT_THRESHOLD   = 13.234710693359375
```

No normalization, rescaling, inversion, or clipping was introduced.

## Implementation Boundary

The fix is confined to a new harness adapter `backend/evaluation/score_lineage.py::build_retrieval_result`, which converts `(Document, distance)` into a `RetrievalResult` with `vector_score = distance`. The run harness `v376_score_lineage.py` uses it. No protected component was modified.

## Why Threshold Was Not Changed

The threshold `13.234710693359375` is untouched. The defect was score propagation, not threshold calibration. Changing the threshold would conflate two distinct concerns and would have masked the root cause.
