## 3. Contract model

The contract separates the structured claim from provenance:

- `TableStructureClaim` carries resolved document, ownership relation, model scope,
  parameter scope, requested value/action, and optional qualifier/section scopes.
- `TableStructureProof` carries physical table provenance and source anchors.
- `ProofValidationResult` returns only `valid` plus deterministic `reason_codes`.

The proof contains no answer and no identity decision. The fields `answer`, `decision`,
`identity_compatible`, `supported`, and `abstain` are explicitly forbidden.

Core proof fields are:

| Group | Fields |
|---|---|
| Version and source | `proof_id`, `proof_version`, `document_id`, `chunk_ids` |
| Table identity | `table_region_id`, model/parameter/value scope IDs |
| Source text | `model_text`, `parameter_text`, `value_text` |
| Row ownership | model/parameter/value row IDs |
| Column ownership | model/parameter/value column IDs |
| Inheritance | `header_path`, `section_scope_id`, `merged_cell_span` |
| Semantic role | `cell_role`, `qualifier_scope_id`, `reference_target` |
| Safety | `conflicting_owner_ids` |

Scope IDs bind the proof to an already structured claim. Text is retained for citation and
audit; the contract itself does not perform synonym expansion or Identity reasoning.

## 4. Relation invariants

Each supported `TableOwnershipRelation` has distinct required fields and checks:

| Relation | Required invariant |
|---|---|
| `DIRECT_ROW` | Parameter and value/action must share the same row; requested value must match. |
| `COLUMN_BOUND` | Model and value must share a row; parameter header and value must share a column; parameter must occur in `header_path`. |
| `HEADER_INHERITED` | The value column must carry an explicit `header_path` containing the parameter scope. |
| `SECTION_INHERITED` | Section scope must be explicit and match the claim; parameter and value must share a row. |
| `CROSS_REFERENCE` | Reference source must be row-owned, cell role must be `REFERENCE`, and target must match exactly. |
| `UNSUPPORTED` | Cannot be submitted as a valid proof. |

Global invariants require exact document/model/parameter/qualifier/section scope matching,
non-empty source chunks, valid positive merged-cell spans, and zero conflicting owners.
Duplicate chunk IDs are rejected.

`validate_proof_lineage` permits one proof to be replicated into multiple chunks while
requiring every structural field to remain identical. Any row, column, header, scope, role,
or reference drift under the same proof ID is rejected.

## 8. Safety and engineering integrity

The contract preserves the V3.50 responsibility split:

- structure producers may describe table facts but cannot emit an answer decision;
- Evidence may validate a supplied proof but cannot invent missing row or column lineage;
- Identity compatibility cannot replace model ownership;
- a conflict always invalidates the proof;
- a missing or invalid proof remains `UNSUPPORTED` at the Evidence boundary.

No family inheritance, manufacturer expansion, parameter borrowing, cross-model leakage,
retrieval expansion, or sufficiency relaxation was introduced.

## 9. Decision

Decision: **CONTRACT_READY**.

The typed proof contract is sufficient for development-level schema semantics. It expresses
the distinctions that flattened proximity could not: row ownership, model-row ownership,
column/header lineage, section ownership, explicit reference source/target, conflicts, and
stable cross-chunk provenance.

This decision does not mean parser implementation is ready. It means the contract itself is
internally consistent on registered fixtures and is safe enough to undergo independent
generalization before any component is unfrozen.
